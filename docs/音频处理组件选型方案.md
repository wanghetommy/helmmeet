# 音频处理组件选型与接入方案

日期：2026年10月19日 · 状态：AP03a降噪与AP03b外放AEC实验版已接入，默认关闭；真人质量/设备与长时待验收

本方案回应成熟组件复用要求。已有 AVAudioEngine / ScreenCaptureKit 采集继续使用；本次先修转换器输入内存复用缺陷，不能用降噪掩盖程序制造的断裂。原始麦克风录音一旦存入错误波形，升级组件不能自动还原缺失人声。具体复现见[音频连续性修复验证](./音频连续性修复验证.md)。

## 1 选型结论

**建议采用 WebRTC Audio Processing Module（APM）作为可选语音增强主引擎，现有系统采集与 Apple 连续采样率转换保持独立。** 首先完成本地离线实验、arm64 静态构建和质量比较，再作为产品功能交付。不要为使用 APM 引入完整浏览器、RTC 网络栈或会议入会服务，也不自行实现回声消除算法。

macOS 原生 Voice Processing 作为对照候选，RNNoise 作为后续降噪替换项，SpeexDSP 作为轻量备选。默认不叠加多套 AEC、降噪和自动增益。

以下适用性与优先级是结合本项目架构的判断，不是项目已跑出的音质排行。

| 组件 | 官方能力及许可入口 | 在 HelmMeet 中的位置 | 取舍 |
| --- | --- | --- | --- |
| [WebRTC APM](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h) | AEC、NS、AGC；采集与参考两流，约10ms帧；[BSD许可及PATENTS入口](https://webrtc.googlesource.com/src/+/refs/heads/main/LICENSE) | 主选：本机麦克风增强；系统声音作为AEC参考并单独保留 | 功能完整，可独立使用；C++依赖、打包及时间对齐需要工程验证 |
| [RNNoise](https://github.com/xiph/rnnoise) | 神经网络降噪，BSD-3-Clause；[示例](https://raw.githubusercontent.com/xiph/rnnoise/main/examples/rnnoise_demo.c)使用480样本帧 | 噪声场景的独立对照或NS替换项 | 不提供AEC；官方示例要求48kHz链路，当前16kHz文件升采样不会恢复高频；模型随构建锁定打包，不在会议中下载 |
| [SpeexDSP](https://github.com/xiph/speexdsp) | AEC、预处理、流式重采样；[BSD许可](https://raw.githubusercontent.com/xiph/speexdsp/master/COPYING) | 依赖/体积受限时的对照 | C接口较直接；质量仍需同数据比较，不因成熟或体积小就预设胜过APM |
| [Apple Voice Processing](https://developer.apple.com/videos/play/wwdc2023/10235/) | 系统AEC、NS、AGC，AUVoiceProcessingIO或AVAudioEngine模式；非开源库 | macOS原生对照候选 | 无额外第三方DSP库；其他应用音频、设备路由、ducking及原始轨保留边界必须实测，不能承诺开启一个开关即覆盖第三方会议软件 |
| [DeepFilterNet](https://github.com/Rikorose/DeepFilterNet) | 48kHz语音增强，含Rust实现与模型；仓库有MIT/Apache许可文件 | 后续较强降噪对照 | 非AEC替代；需要额外模型、时延与打包评估，不作为本次修复依赖 |

WebRTC可优先实验[独立APM发行项目](https://gitlab.freedesktop.org/pulseaudio/webrtc-audio-processing)；已查到官方[2.1发行记录](https://cgit.freedesktop.org/pulseaudio/webrtc-audio-processing/commit/?id=846fe90a289f58b7c9303a635142aa2c7caa93e5)。发行库与WebRTC当前主分支的API/算法代际不能混为一谈，不能将主分支示例直接套到固定发行包。尚未在本项目构建该库，也未验证第三方Rust封装；不承诺现成crate直接可用。若独立版本在Darwin上不满足要求，再评估固定WebRTC官方提交的最小APM构建。

## 2 回声消除的关键输入

AEC需要两条分开的信号：麦克风采到的“本人+扬声器回声”，以及实际送往扬声器的远端播放参考。不是对混合音轨简单降噪，也不是拿两轨同采样点相减。参考必须覆盖实际扬声器声音、与麦克风时间对齐并保留路径延迟；[Speex官方说明](https://www.speex.org/docs/manual/speex-manual/node7.html)和[WebRTC接口](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h)均要求参考/采集流配合。

HelmMeet的系统声音来自第三方应用，ScreenCaptureKit采样时间与实际扬声器播放仍可能有延迟、路由差异或蓝牙变化。按主机时间建参考队列，校准并估计延迟；双人同时说话时检查近端人声是否被误消除。参考缺失/延迟失效应标记AEC不可用或旁路，不能拿未来帧、伪造参考或阻塞原音频保存。

不将会议软件处理后的远端轨再次强降噪，也不把系统轨送入麦克风AEC的采集入口。应用不重新播放系统轨来制造参考，避免形成回授。仅麦克风模式不因启用AEC而暗中扩展系统声音采集；需要参考时向用户明确音源和权限要求。

## 3 接入架构

```text
AVAudioEngine麦克风 → 安全缓冲/连续转换 → 原始麦克风轨落盘
                                         └→ 10ms组帧 → APM采集处理 → 派生增强轨
ScreenCaptureKit系统声音 → 连续转换 → 系统原轨落盘
                              └→ 主机时间/延迟参考队列 → APM参考流
增强麦克风 + 系统原轨 → 固定混音增益 → 转写/回听/导出所选音轨
```

- 初始实验优先复用当前16kHz单声道，每帧160样本，避免第一步同时改存储格式。APM版本支持的速率/通道以固定头文件和实测为准。
- RNNoise/DeepFilterNet对照需要另设48kHz处理支路；若以后提升原轨为48kHz，单轨16bit PCM约346MB/小时，双轨约691MB/小时，另有派生音轨开销，应有容量与清理策略。
- 新建 `native/audio-processing/` 最小C ABI封装，Rust负责有界队列、配置版本和处理状态；不把库对象或音频指针暴露前端。实际目录和代码在实施时创建，不把本调研算已接入。
- 原音频先保存；增强在有界后台工作或落盘后派生。处理积压不丢原轨，不阻塞采集。增强失败保留原轨、明确旁路/缺失范围与处理配置，不默默混用并声称全程增强。
- 每路保留连续状态与分数相位；任意输入包重新组帧，暂停、真实缺口和设备变更明确flush/reset。记录处理延迟，引用与回听时间仍指向真实会议时间，不能悄悄裁掉开头来对齐。
- 派生轨标记引擎版本、参数、源轨及时间覆盖；回听/导出可选原始或增强。原轨不重写，历史分析与引用不因重算无声变化。
- APM增强流与Apple Voice Processing互斥；NS先用轻度/中度，AGC先关闭或保守实验，避免放大底噪和重复处理。线下多人会议尤其检查远处发言被“语音隔离”误抑制。

## 4 产品行为建议

音频设置提供“保留原声 / 语音增强”，具体引擎属于高级诊断，不要求普通用户理解算法名。回声消除仅在具备有效参考的适用音源模式下可用；不足时说明原因。耳机、外放、线下多人、仅电脑声音分别有测试配置，避免一个默认预设覆盖所有场景。

此次不默认打开任何新DSP，不更改原轨或启用额外采集。新功能经过质量验收后再定默认值。

### 6.2 首版产品范围与默认行为

- 全局只增加默认语音增强偏好，本场准备可覆盖；首版在开始录制时冻结引擎/参数快照，会中不热切算法。原声/增强回听切换不改变本场采集和转写。
- 实验版增强默认关闭，用户主动开启。先提供轻度/中度，自动增益关闭；不使用强语音隔离作为线下多人默认。正式默认待质量数据后确定。
- 原轨优先落盘，增强从已保存且连续的原轨派生；处理与ASR分别排队，有界积压不会拖住暂停/结束。增强未跟上时说明覆盖状态，不把原声片段静默拼入“全程增强”。
- 第一版默认继续使用原轨转写，先验证回听/导出改善。原声与增强ASR在离线质量集中比较；今后若增加增强转写，须显式选择并保存新的来源/修订，不自动重写既有文字。
- 历史会议不批量自动处理。重新生成派生轨只在明确操作后执行，原轨不修改；此次咔哒声修复不能反推历史缺失人声已还原。
- 本轮UI限于音频选项、处理状态和音轨选择，沿用当前页面；不提前引入整体导航、知识库或会前/中/后的整页改版。

| 使用场景 | 建议处理 |
| --- | --- |
| 线下多人、仅麦克风 | 原声或轻度NS，重点保护远处人员；AEC无播放参考时不可用 |
| 线上戴耳机、双源 | 麦克风NS按需，系统轨保持原声；AEC先关闭 |
| 线上电脑外放、双源 | 参考有效时可主动启用AEC，麦克风NS按需；远端系统轨仍保留 |
| 仅电脑声音 | 保持系统原轨，不重复强降噪 |
| 系统参考缺失/路径失效 | 显示AEC不可用/降级，保留原声录制；不扩大音源权限或偷偷启用系统采集 |

### 6.3 实施位置与交付边界

拟新增 `native/audio-processing/`（固定引擎的窄C ABI及合成工具），Rust适配器负责派生任务、音轨索引/配置快照/覆盖、版本栅栏与受限IPC；领域组帧/覆盖规则放meeting-core。已有数据库迁移只追加，明确记录派生轨的源轨、引擎版本和参数。前端只接收处理状态和允许访问的PCM，不持有原生指针或文件自由路径。

删除会议、切会议、取消和退出时阻止旧派生任务写回；同一会议重算保留所选版本。未完成派生任务不能被当作完整增强音轨导出。后台处理失败不使会议录制失败；处理磁盘容量不足须有清理/回退入口。

### 6.4 验收方法与初始目标

1. 合成连续波、静音、语音夹具、稳定底噪、不同延迟/漂移的回声与双讲；任意包大小、真实缺口、暂停和参考丢失；严格检查长度/时间映射、状态、原轨hash和跨场隔离。
2. 同一段固定参数比较原声/增强，记录噪声能量、远端单讲ERLE、双讲近端失真/能量及盲听结果。ERLE仅在适用的远端单讲、有独立参考的窗口计算；不能用静音门限、整体音量变小或牺牲人声换“好指标”。
3. 初始性能目标：目标Mac上10ms处理帧的P95不超过5ms、P99不超过10ms；原轨丢帧为0，队列内存有界、长时不持续积压。这是计划目标，不是本次实测结论；另行记录读盘/队列/算法总延迟。
4. ASR比较使用同一Whisper版本、同一标注集，报告CER和专名错误；不因听感更干净就自动默认增强转写。NS/AEC音质阈值及适用预设在组件实验基线后、正式设备验收前冻结。
5. 实机分开登记：内置麦克风+扬声器、耳机、USB、蓝牙，以及一种原生会议软件和一种浏览器会议。真实采集仅按明确授权执行；自动化先使用合成或已授权离线夹具。

下一次进入开发的具体起点是AP02：锁定组件、完成macOS静态构建和离线处理对照，形成采用记录后接降噪首版。整体产品方案随后再评审，尚未开始其业务改版。
