# 音频增强组件 AP02 实施与验证

日期：2026年10月19日 · 范围：独立组件静态构建、窄C ABI、离线对照、应用体积与性能实验

## 1 交付与采用结论

AP02 已执行：固定 WebRTC Audio Processing 2.1、Abseil 20240722.1，macOS 14+ arm64/NEON 静态构建。新增 `native/audio-processing/`，包含校验下载、离线构建、C ABI与合成实验工具。Rust通过可选 `audio-processing` feature接入显式 `--check-audio-processing` CLI；正常录音/ASR/UI尚未使用增强。

工程结论：独立APM在当前Mac可构建、静态链接并运行，包体和算法调用性能支持进入AP03a降噪派生轨阶段。这里的“采用”是组件工程可行性，不代表人声保护、真实外放回声、CER或完整降噪功能已验收。

## 2 版本、构建与运行边界

- 版本、HTTPS来源和SHA-256在[依赖锁](../native/audio-processing/dependencies.lock.json)，工具wheel另有hash锁。使用上游兼容的Abseil修补版，禁用Meson fallback和隐式下载。源码、构建缓存在忽略的 `.tools/audio-processing/`，真实音频与会议未进入工程。
- 目标显式固定arm64/macOS14，NEON启用；构建环境曾把host报告为x86_64而编译器目标为arm64，已用cross文件消除歧义。初次链接例程发现缺CoreFoundation，显式补系统framework即可，无上游算法补丁。
- pkgconf与Abseil同prefix会过滤其系统include路径，构建环境显式保留这些cflags。项目构建锁串行化共享缓存，归档与工具原子替换。
- C ABI只接受16kHz单声道160样本、有限且幅度[-1,1]的float，NS关闭/轻度/中度，AGC关闭；异常不跨C边界，错误不修改输出。实例单线程独占，Rust RAII释放且不可Send/Sync。
- AEC基础接口拒绝缺参考、已消费参考、无效延迟或reset后的陈旧参考；实际参考时间映射、路由与延迟估计尚属AP03b。不能把接口能运行当作实际AEC通过。
- 程序不抓取麦克风、系统声音或网络，不读真实会议/开发凭据。合成CLI在应用数据、UI和模型初始化前返回。探针之外不改变默认处理。
- [许可文本](../native/audio-processing/licenses/)已保留并随app打包；APM内部RNNoise/VAD、PFFFT等子组件与后续独立降噪引擎选型分开。应用只依赖系统C++/Foundation/CoreFoundation，无额外APM/Abseil动态库。

## 3 可复现命令

```sh
.tools/python/bin/python3 -m pip install --require-hashes -r native/audio-processing/build-requirements.txt
python3 native/audio-processing/build.py --download
# 缓存就绪后的离线构建
python3 native/audio-processing/build.py
.tools/audio-processing/bin/apm-probe --self-test
.tools/audio-processing/bin/apm-probe --benchmark /private/tmp/helmmeet-apm-synthetic 6000
sh scripts/with-toolchain.sh cargo test --workspace --locked --features audio-processing
sh scripts/with-toolchain.sh cargo clippy --workspace --all-targets --locked --features audio-processing -- -D warnings
npm run desktop:build -- --features audio-processing
target/release/bundle/macos/HelmMeet.app/Contents/MacOS/helmmeet-desktop --check-audio-processing
```

构建命令会保持正常录制行为；`--check-audio-processing` 是主动合成测试，不是用户会议增强入口。无feature应用对同参数明确exit2，不打开GUI/数据库。

## 4 测量口径与结果

环境：Apple M5 Pro、48GiB内存；Apple clang21、macOS26.6.2、macOS14部署目标；实际架构由Mach-O检查为arm64。原始机器可读结果在忽略目录 `artifacts/audio-processing/`，仅含合成音频、引擎信息和指标；复现不依赖该目录已存在。

### 静态库

| 项目 | 实测字节 | MiB |
| --- | ---: | ---: |
| APM所有静态归档 | 2,478,856 | 2.36 |
| Abseil静态归档 | 1,863,136 | 1.78 |
| 桥接+APM+Abseil合并归档 | 4,338,608 | 4.14 |
| 链接后的离线工具 | 751,632 | 0.72 |

静态归档含未用对象，不能拿4.14MiB直接当应用增量。工具经dead-strip只带实际依赖；`otool -L`仅列系统库/framework。

### 应用实际增量

同一代码、相同许可证资源与签名方式，分别构建feature关闭/开启版；统计app内普通文件逻辑字节总量，不统计目录分配块或符号链接重复目标。

| 构建 | App文件字节 | MiB |
| --- | ---: | ---: |
| 无APM feature | 13,223,498 | 12.61 |
| 有APM feature | 13,903,562 | 13.26 |
| 增量（含依赖） | **680,064** | **0.65** |

可执行文件本身从13,176,800增至13,856,864字节，差值同为680,064。打包工具报告的13.32MiB与逻辑文件求和口径不同；不是把Linux库大小外推为macOS结果。新包3次显式合成CLI通过，帧P95为0.0040–0.006708ms，均无stderr、未创建指定的测试数据目录。签名校验通过，`otool`未出现本机`.tools`或APM/Abseil动态库路径。

### 算法性能与合成对照

三次独立进程，每次60秒/6000帧、固定种子、16kHz谐波+噪声，NS中度且AEC/AGC关闭；排除100帧预热。P95为0.003208–0.003416ms，P99为0.003458–0.003792ms，最大单帧0.014667–0.044667ms；整段处理循环wall为17.8709–18.5924ms。

实时单核等效负载为0.0298%–0.0309%（进程CPU秒/60秒音频×100），不是未限速benchmark运行期间的即时CPU占用率。三次RSS峰值为17,809,408–17,825,792字节，约16.98–17.00MiB，是整个工具进程，包含三份音频数组，不能声称是APM独占内存。算法耗时不含采集/读写盘/排队，不是用户端到端延迟。

合成噪声窗口能量下降11.52dB；仅说明该固定合成条件下NS在工作，不作为真实语音保真或ASR准确率证据。原声、干净谐波、增强WAV是本地可比较夹具，未播放或外发。当前无基于真实语音的盲听、CER、功耗或AEC实机结果。
